- No se tocó `system.odin` ni `lib/dbus`.

**Portado / diseño (no hay Go: upstream usa la UI Tauri).** Misma API en ambos SO:
- `send` → `Notify` `susssasa{sv}i` → `u`; `close_notification` → `CloseNotification(u)`; `get_server_information` → `(ssss)`; `get_capabilities` → `as`; `subscribe` → señales `NotificationClosed(uu)`, `ActionInvoked(us)`, `ActivationToken(us)` entregadas como `Signal` (mismo `Close_Reason`, razón fuera de 1..4 → `.Undefined`) en un hilo lector.
- **Una sola conexión de bus por proceso (con refcount)**: dunst (y GNOME/KDE) emiten `ActionInvoked`/`NotificationClosed` como señales **unicast** a la conexión que hizo `Notify`; en Windows notifyd hace broadcast a cada suscriptor. Por eso `Conn` en unix es una referencia a la conexión compartida: el `Subscriber` y los `send` usan la misma (test: `connections == 1`). Al cerrar la última referencia se cierra el bus.
- `connect()` = bus + sondeo `GetServerInformation`: sin bus de sesión, dirección inválida o sin dueño del nombre (`ServiceUnknown`/`NameHasNoOwner`) → `.No_Server` (las notificaciones quedan sólo en el historial, como antes). Errores remotos → `.Server_Error`; firma/valor inválido → `.Protocol`; IO/timeout/cerrado → `.Io` (`call_timeout` = 10 s: el puente tiene su lock tomado durante la llamada).
- El hilo del suscriptor termina (equivalente al pipe roto en Windows) si el bus se cae o si `NameOwnerChanged(org.freedesktop.Notifications, old≠"", ...)`: `system.odin` lo ve con `thread.is_done(sub.thread)`, reconecta y reenvía. Las señales unicast saltean las match rules del bus: sólo se aceptan las del `sender` que respondió el sondeo.
- Dirección: `set_bus_address()` (tests) > `$WNOTIFY_PIPE` (en unix es una dirección D-Bus) > bus de sesión (`$DBUS_SESSION_BUS_ADDRESS`, `$XDG_RUNTIME_DIR/bus`).
- **Hints**: se conservan en forma textual (la del protocolo de Windows) y se convierten a variantes tipadas: `s b y n q i u x t d` + `image` (`w:h:rowstride:alpha:bps:channels:<base64>` → `(iiibiiay)`, validando bps 8, canales 3/4 y largo según rowstride; la última fila puede ser corta, como dice la spec).
- **Iconos**: `app_icon` tal cual (string); `image-path` como string; y si el llamador no dio un hint de imagen, el PNG de `image-path` (o de un `app_icon` absoluto / `file://`) se decodifica con `core:image/png` (`.alpha_add_if_missing`, 16 bits → byte alto) a RGBA crudo y se adjunta como `image-data` `(iiibiiay)` = (128, 128, 512, true, 8, 4, 65536 bytes) para `pm_light_128.png`. Caché de un ícono (path + tamaño + mtime). `attach_image_data` / `max_image_side` (1024) configurables. Los “toast images” son del lado Windows (notifyd importando toasts): no existen en D-Bus.

**PORT-TODO(darwin)** (`wnotify_other.odin`): macOS no tiene bus de sesión D-Bus por defecto → `.No_Server`; nativo requeriría `UNUserNotificationCenter` (ObjC, bundle firmado), fuera de `core:sys/posix`. No queda `PORT-TODO(unix)`.

**Bugs encontrados.** Corregido (Windows, wnotify): el endpoint por defecto era `` `\.\pipe\org.freedesktop.Notifications.<sid>` `` (falta una barra: ruta relativa a la raíz del disco) → sin `WNOTIFY_PIPE` Portmaster nunca encontraba a notifyd; ahora `\\.\pipe\...` y hay test. Los tests no lo veían porque siempre fijan `WNOTIFY_PIPE`. `lib/dbus`: sin bugs encontrados, no se tocó.

**Trampas.**
1. Señales unicast: suscriptor y emisor en conexiones distintas (como en Windows) → `ActionInvoked` nunca llega con dunst real → conexión compartida con refcount.
2. `png.destroy` libera metadata con `context.allocator`, no con el allocator del load → "bad free" del tracking allocator → decodificar con `context.allocator = heap()`.
3. Un paquete de test sin `@(test)` para el target (wnotify en Windows antes) no linkea (`relocating against symbol that is in a removed section: __$all_tests_array`) → test portable del codec.
4. Heredoc de bash convirtió `"GetCapabilities\n"` en un salto de línea real (aviso de BRIEF-COMUN) → editar con Edit/python.
5. Un mismo hilo no puede bloquear en dos `Subscription` → `next_signal(signals, 50 ms)` + `next_signal(names, 0)` por vuelta.
6. `$WNOTIFY_PIPE` de los tests de base/notifications (`\\.\pipe\...`) en unix no es dirección D-Bus → `.No_Server`: los tests existentes siguen herméticos sin cambios.

**Abierto.** Un core corriendo como servicio del sistema (root, sin bus de sesión en su entorno) obtiene `.No_Server` — igual que el servicio de Windows en la sesión 0 frente al pipe del usuario; llegar al bus de cada usuario (`/run/user/<uid>/bus` con credenciales de ese uid) es un diseño aparte. `image-path` se manda como ruta absoluta (dunst/libnotify la aceptan; la spec prefiere `file://`).
